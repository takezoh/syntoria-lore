# Identity cutover

This procedure renames the Keycloak realm, clients and client scopes in place and updates protocol-mapper names offline, as part of the [naming cutover](deployment.md#naming-cutover). It preserves the existing realm and mapper IDs, user identity, credentials, grants and mapper configuration, and never creates or recreates identity objects. The deployment sequence and activation gates are in [deployment](deployment.md); the general commands are in the [infrastructure runbook](infrastructure-runbook.md).

The mapper maintenance tool accepts only Keycloak `26.8.1` and an immutable image reference. It also verifies the exact supported database schema and Liquibase history before reading or changing identity rows. A schema or image mismatch is a hard stop; do not edit the tool's expected fingerprints to force a match. The tool updates only the four configured `protocol_mapper.name` fields. The baseline covers the database identity, all realm rows, all client IDs, all client-scope rows, every protocol-mapper row, and every mapper-config row.

## Preconditions

Before scheduling the change, refresh the deployment and database readbacks. Confirm that the pinned Keycloak image is the existing image, the target realm and configured internal IDs match the current inventory, and the source and target names are unambiguous. Store an encrypted database backup and prove that its restore is usable. Have an operator with permission to run `pg_control_system()` and `ALTER DATABASE` available. The target and control database URLs must reach the same PostgreSQL cluster, while the control URL must select a different database.

Designate one isolated maintenance Keycloak, pinned to the approved image and separate from every ordinary Keycloak instance. Use only this instance and the existing in-place Admin API operation to rename the realm, clients, and client scopes while preserving their IDs. Then stop the maintenance instance and every ordinary Keycloak and other identity-database consumer; drain connections, pause queues, jobs, schedulers, and dispatch, and prevent automatic restarts. Keep the independent provider network fence restricted to the operator maintenance endpoint while the maintenance instance is stopped. Before changing admission, the tool takes a session advisory lock in the target database. A concurrent tool run that cannot acquire the lock stops before touching the gate. The tool then closes PostgreSQL connection admission and checks that no other client backend remains before it takes table locks; this database gate does not replace stopping or externally fencing the service.

## Capture and apply

Provide the target and control URLs through protected environment injection. Do not put passwords in command arguments or shell history. Capture a fresh baseline after the Admin API rename and before changing mapper names:

```sh
npm run identity:mapper-names -- --capture-baseline /secure/path/identity-mapper-baseline.json
```

The baseline writer creates a new file with mode `0600` and refuses to overwrite an existing path. Keep the file outside the repository and do not publish it; it contains the full identity inventory. The tool verifies that the file is private and is not a symbolic link when it is later read.

Run the cutover using the same target/control URLs and the captured baseline path:

```sh
npm run identity:mapper-names
```

The tool closes new database connections through a separate control connection, checks for remaining sessions, and applies the name-only update in a serializable transaction with bounded statement, lock, and idle-transaction timeouts. It locks the Keycloak identity and Liquibase tables, checks the pinned schema/history, compares all captured rows, and verifies the complete readback before it restores connection admission. A successful result reports the direction and number of changed names; an unchanged repeat reports `already-applied`.

## Verify and recover

After the mapper tool reports success, keep ordinary Keycloak instances and every other identity consumer stopped; keep queues, jobs, schedulers, autoscalers, and dispatch paused. Start only the designated isolated maintenance Keycloak, still pinned to the approved image, and allow its identity-database path alongside the operator verification endpoint. Read the realm, clients, client scopes, and protocol mappers back through its Admin API. Compare every internal ID and mapper configuration with the private baseline; only the four requested mapper names may differ. Run OAuth token and identity checks for the canonical issuer, audience, and separate read/write scope behavior, and verify existing user login and account settings, required actions, credentials, grants, and key fingerprints. Do not call application API or MCP endpoints while their ordinary services are stopped. SQL success alone does not complete the cutover. If any SQL, Admin API, or OAuth identity check mismatches, stop the maintenance Keycloak, close target-database admission through the separate control database, and verify `datallowconn=false` before escalating.

After SQL, Admin API, and OAuth identity checks pass, stop the maintenance Keycloak and restore the other runtime roles' recorded login states and original network routes. Start the ordinary Keycloak, API, and worker services with dispatch paused, check readiness, and run fresh API/MCP smoke checks for the canonical issuer, audience, and separate read/write scope behavior. Resume dispatch only after those checks pass. If readiness or an API/MCP smoke check fails, keep dispatch paused and resolve it before proceeding.

If a normal transaction failure occurs, the tool rolls back and attempts to reopen database admission while it still owns the target-database advisory lock. Before closing admission it reserves a readback connection. If commit acknowledgement is uncertain, it destroys the uncertain connection, transfers the advisory lock to that reserved connection, and reads back while admission remains closed. An exact target-state readback permits normal verification and reopening. If lock transfer or readback fails, the state is mixed beyond the configured mapper names, or a complete readback fails after commit, the tool leaves admission closed. If reopening admission itself reports an error, treat its state as uncertain and verify `datallowconn` through the control database.

When admission remains closed and both tool connections are gone, do not try to connect directly to the target database. Keep every Keycloak and other identity consumer, queues, schedulers, jobs, autoscalers, dispatch, and automatic restarts externally stopped or paused. Verify their state in the deployment control plane. Enforce and verify an independent provider network fence that permits the target database only from the authorized operator maintenance endpoint and denies all service, worker, job, scheduler, and ordinary Keycloak networks. The PostgreSQL admission flag is database-wide; it is not a maintenance-only access control. If this independent fence cannot be established, leave admission closed and escalate. Where the operator can safely alter runtime login roles, record each role's original `LOGIN` state, set runtime roles to `NOLOGIN`, and verify there are no existing target-database client sessions; `NOLOGIN` does not terminate existing sessions and does not replace the network fence.

With the external fence still in force, use the separate control database to inspect `datallowconn`, then temporarily set target-database admission to `ALLOW_CONNECTIONS true` for the maintenance window. Connect only from the fenced operator endpoint with the controlled maintenance identity. Confirm from the control database that the target has no client sessions other than the maintenance readback session, and confirm runtime roles remain unable to log in. Capture a diagnostic full-row readback to a new mode-`0600` file, for example with `npm run identity:mapper-names -- --capture-baseline /secure/path/identity-mapper-recovery-readback.json`. Compare that private readback with the original private baseline supplied to the failed run: database identity, schema/history, realm/client/scope rows and IDs, all mapper rows, and every mapper-config row must match; only each configured mapper's exact source or target name is permitted to differ. Never replace the original baseline with this diagnostic file or use a changed state as a new baseline. Keep file contents out of terminal output, logs, and tickets; report only sanitized status, counts, or digests.

If the full comparison matches the original baseline apart from those configured mapper names, rerun the same forward command with the original baseline while the operator-only network fence remains active. The tool will serialize the retry, close admission, and perform its own complete SQL readback before reopening it. If any other row, ID, configuration, schema, or database-identity value differs, immediately close admission again through the separate control database, terminate the maintenance session, verify `datallowconn=false`, and escalate without rebaselining or restoring an old snapshot over later writes.

After an exact baseline comparison and successful retry, require the tool's complete SQL readback and restored database admission. Then restore `LOGIN` only for the existing identity-database credential needed by the maintenance Keycloak; change the provider network fence to allow only that isolated, pinned maintenance Keycloak and the operator verification endpoint. Start only that Keycloak. Perform Admin API name readbacks and OAuth token and identity checks for issuer, audience, user login, and scopes through this limited path; all other consumers and dispatch remain stopped or paused. Do not call ordinary API or MCP endpoints while their services are stopped. On any SQL, Admin API, or OAuth identity mismatch, stop the maintenance Keycloak, reclose target-database admission through the control database, verify `datallowconn=false`, and escalate. Once these checks pass, stop the maintenance Keycloak, restore the other runtime roles' recorded login states and original network routes, and start ordinary Keycloak, API, and worker services with dispatch paused. Check readiness and run fresh API/MCP smoke checks before resuming dispatch. Keep dispatch paused if readiness or an API/MCP smoke check fails. Do not restart consumers against an uncertain identity result.

## Rollback

If target consumers have already written data, stop and drain them before rollback. Retain post-cutover writes and reverse only the configured identity names and settings; never restore an old database snapshot over new writes. Keep ordinary Keycloak instances, queues, jobs, schedulers, autoscalers, and dispatch stopped or paused. If rollback is needed before ordinary consumers resume, stop the maintenance Keycloak and keep the target realm, client, and scope names in place while you capture a fresh full baseline to a new private path:

```sh
npm run identity:mapper-names -- --capture-baseline /secure/path/identity-mapper-rollback-baseline.json
```

Keep the provider network fence operator-only while the maintenance Keycloak is stopped. Point the baseline-file environment variable at the new private file and run the reverse command from the fenced operator endpoint:

```sh
IDENTITY_MAPPER_BASELINE_FILE=/secure/path/identity-mapper-rollback-baseline.json npm run identity:mapper-names -- --reverse
```

The tool validates the target realm and scope names even during reverse maintenance; require its complete SQL readback and restored admission. If SQL readback or admission restoration fails, leave consumers stopped, close admission through the separate control database, verify `datallowconn=false`, and escalate without rebaselining or restoring an old snapshot. After SQL verification passes, restore `LOGIN` only for the existing identity-database credential needed by the maintenance Keycloak, allow network access only for that same isolated, pinned maintenance Keycloak and the operator verification endpoint, and start only the maintenance Keycloak. Use its Admin API to restore the source realm, client, and scope names while preserving IDs. Read all identity names and mapper configuration back through the API, and run OAuth token and identity checks for the restored issuer, audience, user login, and scopes. Do not call application API or MCP endpoints while ordinary services are stopped. If an Admin API or OAuth identity check mismatches, stop the maintenance Keycloak, close admission through the separate control database, verify `datallowconn=false`, and escalate.

After SQL, Admin API, and OAuth identity checks pass, stop the maintenance Keycloak, restore the other runtime roles' recorded login states and original network routes, and start ordinary Keycloak, API, and worker services with dispatch paused. Check readiness and run fresh API/MCP smoke checks against the restored issuer before resuming dispatch; keep dispatch paused if readiness or a smoke check fails. Preserve all old resources until the restored identity, OAuth, and API/MCP checks pass. Cleanup requires separate authorization.
