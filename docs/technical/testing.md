# Verification design

## Environment and harness selection

Verify the actual responsibility boundary. Unit tests establish the deterministic value model. The emulator suite establishes the Firestore repository, capture and recall contracts against a local Firestore emulator. Managed IAM, real transaction contention, latency, cost, managed restore, Firestore vector search and hosted identity need separate hosted evidence. A passing lower-fidelity check never closes a higher boundary. Record failed, skipped and unexecuted scenarios explicitly.

## Layers and contracts

- **Unit** (`npm run test:unit`): `tests/memory-records.test.ts` checks validation of the stored shape, rejection of unknown keys, lifecycle, approval and time selectors: a proposal is never a decision, supersede and retract stay distinct, and valid time and known time are selected independently. `tests/api-config.test.ts` checks that the service configuration fails fast and reports every invalid or missing variable, including the cursor key ring and the production bans on loopback HTTP and deterministic embeddings. `tests/access-jwt.test.ts` checks Access assertion verification: issuer, exact audience, expiry, signature, owner email, service-token rejection and key-service outages. `tests/api-embeddings.test.ts` checks the Vertex AI request shape and vector validation with a fake fetch, not a real model. It runs every test file except `*.firestore.test.ts`.
- **Observation ledger** (`tests/observations.test.ts`, and `tests/api-mcp.firestore.test.ts` on the emulator): the unit file checks validation, tiers and the course of a topic: an earlier state stays when a later one follows, the view is the same whatever the order of arrival, a late report of an earlier time does not take over, equal values from different writers count as agreement, a missing value gives `unknown`, a lower tier that disagrees stays an open conflict, a retraction counts only from the same writer or an equal or higher tier, a state dated in the future is upcoming, and a past date is answered from everything known now. The API file drives the service through the `@modelcontextprotocol/client` Streamable HTTP client with locally signed Access assertions, one service instance per admission and deterministic embeddings: 401 for a missing, opaque or malformed credential and 403 for another owner or a missing admission, a provisioned further connection with its own principal and the same 404 for unknown, malformed and foreign connection paths, the tool list and server instructions, write and replay, a request that tries to set the tier, the present, the course and a past date, name lookup through a katakana alias in a question without spaces, term-only and meaning-only results, trust across the default connection and a further connection, alias conflicts, subject and topic links and their revocation, Forget by observation, source and subject with the topic rebuilt, conversion of Memory Records and Forget of the record behind a converted observation, `user_required` under another policy, writer suppression, and an observation hidden by a suppression document alone as after a restore. It does not exercise Cloudflare Access, Vertex AI, IAM, Cloud Run or enforced indexes.
- **Firestore repository, capture and recall** (`npm run test:firestore`): every `tests/*.firestore.test.ts` file against a loopback Firestore emulator. The repository suite checks commits, idempotency, revision races, approval provenance, source rights, suppression, stored-record identity and authority on writes and reads, approved compartment relaxation, Forget acknowledgment against a deterministic independent ledger fake, purge, restore checkpoints, candidate recall opt-in at the repository selector, rights and allowance checks, and feed cursors. The capture suite checks consent and range gating, exact cited-text matching, candidate persistence, source-body exclusion and repeated-lineage idempotency. The derived-recall suite checks revision-fenced term and embedding entries, Japanese term candidates, ranking of a named record above records that share only common terms, the reported match reasons, the current index (bounded rebuild, replacement on a new revision, and past-time questions still served from per-revision entries), stale job ordering, the unindexed-change overlay, rights rechecks and bounded Context Packs; deterministic embeddings prove the port contract only, not semantic recall quality. The API suite (`tests/api-mcp.firestore.test.ts`) starts the HTTP service in-process on both emulator databases, one instance per admission, with locally signed Access assertions and deterministic embeddings, admits subjects with `scripts/admit-subject.mjs`, provisions further connections with `scripts/manage-connections.mjs`, and drives it through the `@modelcontextprotocol/client` Streamable HTTP client: 401 without a valid assertion and no protected-resource metadata, 403 without an admission, query-only recall schema and calls, initialization with concise server instructions, proposal recall by default and opt-out, authority ranking and historical recall, Forget with a ledger head that advances once, structured source roundtrips and correction preservation/replacement/clearing, strict source bounds, idempotent replay and key reuse, a rejected write outside the connection's allowance, `as_user` authority through the `automatic` policy, `user_required` under another policy, and reconciliation of a scope behind the ledger. It does not exercise Cloudflare Access, Vertex AI, IAM or Cloud Run. The workspace suite (`tests/workspaces.firestore.test.ts`) runs `scripts/manage-connections.mjs` against the emulator and checks workspace creation and name conflicts, grant validation, a further connection's allowance and epoch, the access history, that a connection granted one workspace neither reads, finds by term nor receives in the change feed anything of another workspace or the Inbox and cannot write there, that an observation stored before labels existed reads as an Inbox item, and that a changed or deactivated grant takes effect on the next request; `tests/workspace-labels.test.ts` checks the label rule as a unit. The project suite (`tests/projects.firestore.test.ts`) checks creation, renaming, moving and deletion of projects against the four-level limit, name conflicts under a parent, cycles, moves across workspaces, deletion of a project with children or observations, the access history, and that a connection sees and changes only the projects of its granted workspaces; `tests/projects.test.ts` checks the hierarchy rules as a unit, and the API suite manages projects through `list_projects` and `manage_project`. The placement suite (`tests/placement.firestore.test.ts`) checks that observations record workspace, project and scope with the narrowest scope by default, that a wider scope is approved by the `automatic` policy and refused with `user_required` under another, that a placement depending on stored data fails with one message while a malformed request is told why, that a Shared lesson reaches another workspace's connection with its origin and derivation hidden, that `derived_from` must be visible to the writer, that a writer's arrival relation ignores states it may not see, that a deletion marker reaches only connections that could see the forgotten observation, that a write without a workspace needs the Inbox grant even when Shared, that names resolve only through alias entries a reader may see while another workspace's entries for the same name are kept, that a subject ID or a link member outside the allowance reads like one that does not exist, and that a link is followed only by readers of the workspace it was written in; it also checks placement queries through `get_timeline`, `recall` and `list_observations`, `usable` in a context, a topic computed within a query, the same refusal for an unknown and an ungranted place, and a listing cursor bound to its query and reader. `tests/queries.test.ts` checks the query grammar and the usability rule as a unit. The classification part checks that `classify` moves an Inbox item into a project without changing its content, appends a classification record and a `classify` change-feed entry, updates search and the Inbox listing, takes an observation out of reach of a connection that loses it, replays and conflicts by idempotency key, refuses an item the connection may not classify with the same message as an unknown one while other items proceed, and needs the `automatic` policy. The label-key part checks that an index entry built before a classification does not overwrite the new placement, that a classified subject name resolves in its new workspace, that with 1,050 documents of another workspace naming the same member a reader still finds its own observation by term and meaning, its subject name and its link while the filter-after-read path loses all three, and that the pending-index note counts only work the reader may see. The runner fails when `FIRESTORE_EMULATOR_HOST` is unset or not loopback.

## Runners

| Command | Scope |
| --- | --- |
| `npm run verify:local` | Build, typecheck, lint, format, unit, the Firestore emulator suite, secret scan and dependency audit |
| `npm run test:unit` | Unit suites; emulator-dependent files are excluded unless `VITEST_FIRESTORE=1` |
| `npm run test:firestore` | Repository, capture, derived-recall and API suites against a loopback Firestore emulator |

CI runs build, typecheck, lint, format, unit tests, the secret scan and the dependency audit in [local-contract.yml](../../.github/workflows/local-contract.yml) on push and pull request. It does not run the emulator suite.

## Evidence

Each verification record names the source, configuration, commands, results and limitations, and keeps correctness, latency and user value separate. Dated records live in [docs/eval](../eval/). Measurements against the [service targets](../design/requirements.md#service-targets) need the deployed environment.
